# Assignment 4 Report: Track B Code RAG

## Track Declaration

I chose **Track B, Code RAG**. The starter corpus is the Hugging Face `code_search_net` dataset with the `python` config. The embedding model is `sentence-transformers/all-MiniLM-L6-v2`, the vector database is a persistent Chroma collection, and the generator is the UTSA OpenAI-compatible `Qwen/Qwen3-8B` endpoint.

## Pipeline Summary

The pipeline indexes 1,000 Python functions from CodeSearchNet. For each function, the docstring and source code are concatenated, embedded with `all-MiniLM-L6-v2`, and upserted into Chroma with metadata for `repo`, `path`, `func_name`, and source type. At query time, the same embedding model embeds the user query, Chroma returns the top `k=4` chunks, and Qwen receives a grounded prompt that instructs it to answer only from the retrieved code and cite exact sources as `repo/path::func_name`. Part 2 extends the same collection with five custom Python functions under `data/custom_functions/`, using the same embedding model and metadata schema.

## Reflection

Retrieval succeeded most clearly when the query matched concrete function behavior or docstring language. The Part 2 targeted queries are the cleanest example: all five custom functions were retrieved at rank 1, and the generator produced short grounded answers with exact citations. Part 1 also worked well for concrete starter-corpus topics such as validation, date parsing, HTTP request construction, exception handling, JSON loading, and command-line parser construction.

Retrieval was weaker for broader questions where the nearest dense matches were only adjacent to the intent rather than direct implementations. The clearest example is the summary-statistics query in Part 1, which still returned infrastructure-oriented `get_stats` functions rather than code that actually computes descriptive statistics over numeric sequences, so the generator correctly answered "I do not know based on the retrieved code." Some other broad queries were answerable, but the quality depended heavily on whether the retrieved chunk names and docstrings exposed the intended behavior directly.

The cross-corpus queries showed that the new custom items were successfully inserted into the existing collection. Every cross-corpus row retrieved both a custom function and starter corpus items, and the custom function was rank 1 for all five cross-corpus queries. If I had one more day, I would add a hybrid dense-plus-keyword retriever or a lightweight reranker. That would likely improve cases where exact identifiers, library calls, or rare terms matter more than general semantic similarity.
